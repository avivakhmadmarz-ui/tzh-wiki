# 03 — BI-инструменты

> BI (Business Intelligence — бизнес-аналитика) инструменты — Power BI, Tableau, Looker, Metabase, Apache Superset — слой между сырыми данными и руководителем. Этот раздел — про выбор инструмента под задачу, принципы дизайна дашбордов (Stephen Few), специфику DAX в Power BI и анти-паттерны корпоративных дашбордов.

## Карта раздела

![](attachments/diagrams/11-bi-tools-comparison.svg)

## 1. Ландшафт BI-инструментов

### 1.1 Контекст и легитимность

Современный BI оформился в 2010-х: Tableau (2003, лидер визуализации до 2017) и Power BI (Microsoft, 2014, лидер корпоративного рынка после 2017). Альтернативы — Looker (Google, 2012), Metabase (open-source, 2015), Apache Superset (open-source, 2015). Каноничный обзор — отчёты **Gartner Magic Quadrant for Analytics and Business Intelligence Platforms** (ежегодно).

В РФ после 2022 года ландшафт сместился: Tableau официально ушёл с рынка, Power BI работает через workaround (обходные пути), активно растут open-source альтернативы и российские разработки.

### 1.2 Сравнение основных инструментов

![](attachments/diagrams/11-bi-tools-comparison.svg)

| Инструмент | Сильные стороны | Слабые стороны | Когда выбирать |
|------------|-----------------|----------------|----------------|
| **Power BI** | Дешёвая лицензия, интеграция с Microsoft 365 (Office 365), DAX, доминирует в RU/EU корпоративном сегменте | Менее гибкая визуализация, чем Tableau | Корпоративный стандарт, особенно если уже на стеке Microsoft |
| **Tableau** | Лучшая визуализация, мощный self-service | Дорогая лицензия (~$70+/user/month), в РФ официально недоступен | Когда визуализация — главное требование |
| **Looker (Google)** | LookML (семантический слой), API-first | Дорогой, сложное внедрение | Корпоративная аналитика на Google Cloud |
| **Metabase** | Open-source, простой UI, быстрый старт | Ограничен на сложных моделях | SMB, стартапы, MVP-аналитика |
| **Apache Superset** | Open-source, мощный, активная разработка (Airbnb) | Требует data engineering для внедрения | Tech-стек с DevOps-командой |
| **Российские** | Visiology, Modus, Loginom, Forecast NOW | Меньше функционала, меньше комьюнити | Когда импортозамещение критично |

### 1.3 Тренды 2024-2025

- **Embedded analytics** (встроенная аналитика) — BI внутри SaaS-продуктов, не отдельный портал
- **Self-service** — конечные пользователи строят отчёты сами без аналитика
- **AI-assisted analytics** (Copilot в Power BI, Ask Data в Tableau) — натуральный язык в SQL
- **Real-time dashboards** — обновление в реальном времени, не раз в день
- **Mobile-first** — отчёты в первую очередь для смартфона

**Ключевой вывод 1.** Выбор BI-инструмента — стратегическое решение на 5+ лет. Главные критерии: уже существующий стек данных, бюджет, требования к визуализации, доступность поддержки в РФ.

## 2. Power BI deep dive

### 2.1 Архитектура

Power BI состоит из трёх компонентов:

- **Power BI Desktop** — Windows-приложение для разработки отчётов
- **Power BI Service** — облако для публикации и шеринга
- **Power BI Mobile** — мобильный просмотр

Под капотом — **SSAS Tabular** (SQL Server Analysis Services Tabular) — in-memory колоночное хранилище VertiPaq, оптимизированное для аналитики.

### 2.2 Жизненный цикл отчёта

1. **Подключение к источникам** через Power Query — десятки коннекторов (SQL Server, Excel, REST API, SharePoint, ODBC)
2. **Трансформация в Power Query** — ETL-логика (фильтры, объединения, агрегации, расчётные колонки)
3. **Моделирование** — связи между таблицами (relationships), иерархии, расчётные таблицы
4. **DAX-меры** — формулы для KPI
5. **Визуализация** — графики, таблицы, карточки
6. **Публикация** в Power BI Service
7. **Шеринг и обновление** — расписание refresh, RLS (Row-Level Security — построчная безопасность)

### 2.3 DAX — Data Analysis Expressions

**DAX** (Data Analysis Expressions — выражения анализа данных) — язык формул Power BI. Похож на Excel-формулы, но работает на табличной модели.

**Базовые меры:**

```dax
Total Sales = SUM(Sales[Amount])

Sales YTD =
CALCULATE(
    [Total Sales],
    DATESYTD('Calendar'[Date])
)

Sales LY =
CALCULATE(
    [Total Sales],
    SAMEPERIODLASTYEAR('Calendar'[Date])
)

Growth % =
DIVIDE(
    [Total Sales] - [Sales LY],
    [Sales LY]
)
```

**Главная идея DAX — Filter Context** (фильтрационный контекст). Каждая мера выполняется в контексте текущей строки / выбора слайсеров. CALCULATE меняет контекст; FILTER создаёт условия.

### 2.4 Power Query — M Language

**Power Query** использует язык **M** для трансформаций. В большинстве случаев пользователь работает через UI (кликает мышкой), но для сложных задач — пишет M.

Типичные операции:
- Append (объединение строк)
- Merge (объединение колонок)
- Pivot / Unpivot (поворот таблицы)
- Custom column (расчётная колонка)
- Conditional column (условная колонка)

### 2.5 Главные ошибки разработчиков Power BI

- **Денормализация всего в одну таблицу** — теряется производительность, нарушается логика
- **Слишком много расчётных колонок** в data model — увеличивает размер модели, лучше DAX-меры
- **Связи многие-ко-многим** без правильного направления фильтрации
- **Отсутствие даты-таблицы** (calendar table) — критично для time intelligence функций
- **Visualization overload** — слишком много визуалов на одной странице

**Ключевой вывод 2.** Power BI — это **DAX + правильная модель данных**. UI обманчиво прост; настоящая мощь — в DAX-вычислениях. 80% эффективности разработчика — в моделировании, не в визуализации.

## 3. Принципы дизайна дашбордов

### 3.1 Контекст и легитимность

**Stephen Few** (Стивен Фью) — самый влиятельный автор по дизайну дашбордов. Каноничные книги — **«Information Dashboard Design»** (Analytics Press, 2-е изд. 2013) и **«Now You See It»** (Analytics Press, 2009). Дополнение от Knaflic — **«Storytelling with Data»** (см. заметку 01).

Stephen Few формализовал, **какой дашборд работает, а какой — мусор**. Его принципы — стандарт корпоративного дизайна.

### 3.2 Пять принципов хорошего дашборда

![](attachments/diagrams/11-dashboard-design-principles.svg)

**1. Зачем дашборд?** Чёткий бизнес-вопрос. «Дашборд продаж» — нечто; «дашборд для еженедельного обзора COO с фокусом на отклонения от плана» — конкретика.

**2. Аудитория.** Руководителю нужен top-down view (10-15 ключевых KPI); аналитику — drill-down. Не пытаться сделать «один для всех» — получится плохо для обоих.

**3. Иерархия.** Главные KPI наверху и слева (там, куда падает взгляд). Декомпозиция вниз и вправо. Не «всё одинаково важное» — это шум.

**4. Контекст.** Каждое число с базой сравнения:
- vs прогноз
- vs прошлый период
- vs бенчмарк / конкуренты
- vs цель
Число без контекста — бесполезно.

**5. Визуальная экономия.** Минимум `chartjunk` (визуального мусора): без 3D, без теней, без логотипов, без бессмысленных границ. Каждый пиксель — для данных.

### 3.3 Стандартный layout

Рабочая структура корпоративного дашборда:

```
[Заголовок | Период | Фильтры]
[KPI 1] [KPI 2] [KPI 3] [KPI 4]   ← карточки с главными числами
[Линейный график динамики]         ← главный график
[Bar chart топ-N]   [Структура]    ← разбивки
[Детальная таблица с возможностью drill-down]
```

### 3.4 Анти-паттерны корпоративных дашбордов

- **3D-эффекты** — искажают пропорции
- **Пироги с 8+ сегментами** — нечитаемы
- **Двойные Y-оси** — путают
- **Радар-диаграммы** — нечитаемы при сложных данных
- **«Раскраска для красоты»** — цвет без смысла
- **20 KPI на странице** — выбор без выбора
- **Отсутствие даты обновления** — пользователь не знает, насколько свежие данные

### 3.5 Mobile-first vs Desktop-first

Современный тренд — **mobile-first**: руководитель смотрит KPI с телефона. Это требует:
- Только главные числа на первом экране
- Прокрутка вместо drill-down
- Большие шрифты, минимум деталей

Полные drill-down дашборды остаются для desktop / аналитика.

**Ключевой вывод 3.** Дизайн дашбордов — отдельная компетенция между data analyst и UI/UX designer. Большинство корпоративных дашбордов нарушают базовые принципы. Освоение Stephen Few даёт огромное преимущество в коммуникации.

## 4. Self-service BI и governance

### 4.1 Self-service — конец эпохи «отчётов от ИТ»

Self-service BI — это когда конечные пользователи (категорийные менеджеры, директора) **сами строят отчёты** в Power BI / Tableau без IT-команды.

**Плюсы:**
- Скорость (минуты вместо недель)
- Близость к бизнес-вопросу
- Освобождение IT-ресурсов

**Минусы:**
- Хаос версий («у каждого свой Excel»)
- Несогласованные определения метрик («что такое выручка»)
- Качество данных
- Безопасность

### 4.2 Data Governance — управление данными

Решение проблем self-service — **data governance** (управление данными):

- **Data catalog** (каталог данных) — единый реестр таблиц, метрик, отчётов с описанием и владельцами
- **Semantic layer** (семантический слой) — единые определения метрик (Looker LookML, dbt Semantic Layer)
- **Master data management (MDM)** — единые справочники клиентов, продуктов, регионов
- **Data quality** — мониторинг отклонений, тесты на ETL
- **Access control** — кто что видит (RLS / OLS — Object-Level Security)

### 4.3 Centers of Excellence (CoE)

В зрелых компаниях создаётся **BI CoE** (Center of Excellence — центр совершенства):
- Стандарты разработки отчётов
- Обучение бизнес-пользователей
- Каталог сертифицированных дашбордов
- Поддержка self-service

Без CoE self-service быстро превращается в хаос.

**Ключевой вывод 4.** Self-service без governance = data anarchy. Зрелые компании балансируют: бизнес-пользователи строят отчёты для **собственного** использования; критичные корпоративные дашборды разрабатывает CoE по стандартам.

## 5. Производительность BI

### 5.1 Главные причины медленных дашбордов

- **Слишком много данных** в модели (миллионы строк без агрегации)
- **Слишком сложные DAX-меры** (вложенные FILTER, ITERATOR без CALCULATE)
- **Много визуалов на странице** (каждый — отдельный запрос)
- **Direct Query режим** вместо Import (медленнее, но real-time)
- **Большие unfiltered cross-products** при JOIN

### 5.2 Стратегии оптимизации

1. **Aggregate tables** — предварительно агрегированные таблицы для тяжёлых запросов
2. **Incremental refresh** — обновлять только последний период, а не всю модель
3. **Calculation Groups** (Power BI) — переиспользуемые DAX-меры
4. **Star schema** — соблюдать чистую schema, не денормализовать всё
5. **Profiler / DAX Studio** — инструменты диагностики

### 5.3 Когда обращаться к специалисту

Для руководителя достаточно понимать **симптомы** медленного дашборда. Реальная оптимизация — задача BI Developer или DAX-эксперта.

**Ключевой вывод 5.** Производительность BI — отдельная глубокая тема. Базовая интуиция: меньше данных + правильная star schema + умные меры = быстрый дашборд.

## Сводный практический протокол

Разработка нового корпоративного дашборда:

| Шаг | Действие | Артефакт |
|-----|----------|----------|
| 1 | Определить бизнес-вопрос | One-pager «зачем дашборд» |
| 2 | Сформулировать KPI и метрики | Глоссарий метрик |
| 3 | Спроектировать data model (star schema) | ER-диаграмма |
| 4 | Подготовить ETL (Power Query) | Pipeline данных |
| 5 | Разработать DAX-меры | Список мер с тестами |
| 6 | Спроектировать layout по Stephen Few | Wireframe |
| 7 | Прототип в Power BI Desktop | PBIX файл |
| 8 | Тестирование с конечным пользователем | Список правок |
| 9 | Публикация в Service + расписание refresh | Production-дашборд |
| 10 | Документация и обучение | Wiki-страница |

Стандартный срок от идеи до production — 4-8 недель для среднего дашборда.

## Применение для руководителя

| Целевая роль | Главные применения |
|--------------|---------------------|
| **COO** | Заказчик дашбордов; ежедневное чтение operational dashboard; квартальное review с CDO |
| **Директор закупок** | Self-service отчёты по поставщикам, закупкам, ценам; dashboards для еженедельных встреч |
| **Директор продукта** | A/B-test dashboards; product funnel analytics; cohort analysis |
| **Категорийный менеджер** | Категорийные дашборды (продажи / маржа / оборачиваемость); еженедельные обзоры |
| **CDO / Head of BI** | Архитектура BI-стека; governance; CoE; выбор инструментов |
| **CFO** | Финансовые дашборды (P&L, Cash Flow, working capital); financial planning |
