# 03 — Инструменты Lean: что когда применять

> Инструменты Lean — это не «список фишек», это **набор связанных техник под задачи разной природы**. Использовать их без понимания TPS-философии (см. [[01-Toyota-Production-System|01]]) и без понимания, какую потерю ты атакуешь (см. [[02-8-wastes-Muda-Mura-Muri|02]]) — путь в cargo cult.

## Карта инструментов: что лечит каждый

| Инструмент | Главная цель | Лечит потери | Когда применять |
|------------|--------------|--------------|-----------------|
| **5S** | Организация рабочего места | Motion, Waiting, Defects | На любой неупорядоченной зоне (склад, офис, цех) — стартовая практика |
| **Kanban** | Pull-сигнал, ограничение WIP | Inventory, Overproduction, Waiting | Когда нужно заменить push на pull (производство, склад, ИТ) |
| **Kaizen** | Культура непрерывного улучшения | Все 8 | Постоянно, как способ работы; кaizen events — раз в квартал на конкретную проблему |
| **Value Stream Mapping** | Карта потока ценности | Все 8 (диагностика) | На старте Lean-инициативы — нужно понять, где потери |
| **Poka-Yoke** | Защита от ошибок | Defects | На шагах с высоким риском человеческой ошибки |
| **Andon** | Сигнал о проблеме | Defects, Waiting (через быстрое реагирование) | Везде, где важно мгновенно увидеть отклонение |
| **Heijunka** | Выравнивание загрузки | Mura → Muda | Когда есть пиковая загрузка/простой |
| **JIT** | Производство по сигналу | Inventory, Overproduction | После того, как выстроили pull и стандартизовали |
| **SMED** | Сокращение времени переналадки | Waiting, Inventory | Если переналадка >10 мин и из-за этого работаем большими партиями |
| **TPM** | Эффективность оборудования | Defects, Waiting (от поломок) | Когда поломки оборудования = главная проблема |
| **A3 Thinking** | Структурирование решения проблемы | Все (через root-cause) | Любая проблема, требующая корневого анализа |
| **PDCA** | Цикл обучения/улучшения | Все (метод) | Базовая логика любого улучшения; используется внутри A3 |
| **Standard Work** | Текущая лучшая практика | Defects, Mura | Перед любым kaizen — нечего улучшать без стандарта |

Дальше — каждый инструмент детальнее.

## 5S — организация рабочего места

Пять японских слов на «S» (Sort, Set in order, Shine, Standardize, Sustain).

| Шаг | Японский | Перевод | Действие |
|-----|----------|---------|----------|
| 1 | Seiri | Sort (Сортировать) | Убрать всё, что не нужно для работы |
| 2 | Seiton | Set in order (Упорядочить) | Каждой вещи — своё место. «Место для всего и всё на своём месте» |
| 3 | Seiso | Shine (Чистить) | Чистка = ежедневный осмотр. Грязь часто прячет проблемы (течь, поломку, износ) |
| 4 | Seiketsu | Standardize (Стандартизовать) | Записать, как должно выглядеть; сделать визуальные индикаторы |
| 5 | Shitsuke | Sustain (Поддерживать) | Дисциплина, аудит, ревью |

**Эффект:** в одном из кейсов склада после 5S — pick accuracy выросла с 96% до 99,8%, новые сотрудники выходили на полную производительность за 2 дня вместо 2 недель ([Conger Industries](https://www.conger.com/warehouse-5s/)).

**В твоём контексте (склад, ритейл):**
- **Sort:** убрать с полок просрочку, сломанный паллет, бракованные акционные дисплеи.
- **Set in order:** зонирование склада по ABC, каждой SKU — фиксированный адрес, цветовое кодирование зон.
- **Shine:** ежедневная уборка зон, визуальная инспекция оборудования (рохля, погрузчик).
- **Standardize:** фотостандарт раскладки на полке (planogram), стандартный чек-лист утреннего открытия.
- **Sustain:** еженедельный 5S-аудит со скорингом, KPI на менеджера склада.

**Ловушка:** 5S без последних двух S (Standardize + Sustain) = разовая уборка, которая откатывается за 3 месяца. **Sustain — самое сложное.**

## Kanban — визуальная сигнальная система

Тайити Оно увидел супермаркет в США (1956): покупатель берёт с полки, продавец докладывает. **Покупатель тянет, продавец не толкает.** Это — pull system.

Kanban (看板, «карточка/сигнал») — карточка или иной сигнал «дай мне ещё, я только что использовал».

**Базовое правило:** ничего не производится и не закупается без kanban-сигнала с downstream-этапа.

### Виды kanban

| Тип | Назначение |
|-----|------------|
| **Production kanban** | Сигнал производить новую партию |
| **Withdrawal kanban** | Сигнал переместить материал между процессами |
| **Supplier kanban** | Сигнал поставщику отгрузить новую партию |
| **Two-bin system** | Простой kanban для канцтоваров/мелких деталей: 2 ящика, опустел один — заказ на пополнение |
| **Электронный Kanban** | Trello, Jira, цифровые доски |

### Связь с Agile/Scrum

Современный Kanban в IT (доски с To Do / In Progress / Done и WIP-лимитами) — прямой потомок производственного Kanban. Эрик Шу (David Anderson) перенёс концепцию в разработку ПО в 2007-м.

### Применение в закупках/ритейле

- **Полочный kanban:** под полкой второй ряд товара (карта); опустел верхний — товаровед знает, что нужно дозаказывать.
- **Min/max система:** упрощённый kanban — упал ниже min → автозаказ до max.
- **Kanban для офиса:** триггер «закончились бланки → один на дне ящика — это kanban, заказывай».

## Kaizen — непрерывное улучшение

Японское «kai» (изменение) + «zen» (к лучшему) = **постоянное движение к лучшему маленькими шагами**.

Принципы Kaizen:
1. **Маленькие шаги, всеми, каждый день.** Не «революция раз в год», а 10 000 микро-улучшений в год.
2. **Стандарт → Kaizen → новый стандарт.** Без стандарта улучшать нечего.
3. **Genchi genbutsu** — иди и смотри, не решай в кабинете.
4. **Каждый — улучшатель.** Toyota: ~12 предложений на сотрудника в год, 90% внедряются. Типичная западная компания — <0,5 в год.

### Форматы Kaizen

| Формат | Длительность | Цель |
|--------|--------------|------|
| **Daily kaizen** | Постоянно | Микро-улучшения в течение смены, через систему предложений |
| **Kaizen event / blitz** | 3–5 дней | Сфокусированная команда решает конкретную проблему за неделю |
| **Project kaizen** | Недели–месяцы | Большая трансформация, A3-формат, кросс-функциональная команда |

Подробно в [[04-Cases#Amazon|кейсе Amazon]] — там Kaizen встроен в DNA через ownership culture в two-pizza teams.

## Value Stream Mapping (VSM) — карта потока ценности

Самый мощный диагностический инструмент Lean. Один лист, на котором изображён **весь поток** от клиента до поставщика, с временами.

### Что показывает VSM

```
Поставщик → Процесс 1 → I → Процесс 2 → I → Процесс 3 → Клиент
                       ↑                 ↑
                       Inventory boxes (треугольники)
                       
Tаймлайн внизу:
  ─10 дн.─ 3 мин ─5 дн─ 5 мин ─2 дн─ 2 мин = LT 17 дн, PT 10 мин
                                              PCE = 10 мин / 17 дн = ~0,04%
```

**Ключевые цифры на VSM:**
- **Process Time (PT)** — время реальной работы
- **Lead Time (LT)** — общее время от заказа до отгрузки
- **Process Cycle Efficiency (PCE)** = PT/LT × 100% (норма >25%, мировой класс >50%)
- **% complete and accurate (%C&A)** — процент работы, прошедшей без переделки

### Шаги построения VSM

1. **Выбрать family** — продукт/услугу с похожей маршрутизацией.
2. **Current state map** — нарисовать как есть. Идти физически по процессу с секундомером (не доверяй ERP-данным).
3. **Identify wastes** — пометить на карте 8 видов потерь.
4. **Future state map** — нарисовать целевое состояние.
5. **Implementation plan** — kaizen-burst-зоны и план действий.

### Применение к закупочному процессу

VSM закупочного процесса от заявки до получения товара легко покажет, что:
- 80% времени = waiting (на согласования, на ответ поставщика).
- Только 5–10% — value-add (фактически переговоры и выбор поставщика).

→ Цель: сократить LT с 30 дней до 7, не трогая PT.

## Poka-Yoke — защита от ошибок

«Poka» (ошибка) + «yoke» (предотвращение). Техника **встроенной защиты от ошибки** — невозможно сделать неправильно.

### Два уровня

| Уровень | Что делает | Пример |
|---------|------------|--------|
| **Warning poka-yoke** | Сигнализирует об ошибке | Машина пищит, если ремень не пристёгнут |
| **Control poka-yoke** | Делает ошибку физически невозможной | USB-разъём вставляется только одной стороной (well, до Type-C) |

### Примеры

- **Производство:** форма заготовки такая, что неправильно вставить нельзя.
- **Розетки/вилки:** разная форма для разного напряжения.
- **ATM:** карта возвращается раньше, чем выдаются деньги (чтобы не забыли).
- **ERP:** обязательные поля, валидация формата, contextual hints.

### В закупках/ритейле

- В ERP не дать сохранить заказ без указания даты поставки.
- При вводе SKU автоподстановка наименования (защита от опечаток в коде).
- Сканирование штрихкода вместо ручного ввода артикула.
- При смене ставки НДС — система не позволяет применить старую ставку к новым документам.

**Принцип:** не «обучать сотрудника не ошибаться» (людям свойственно ошибаться), а **переделать процесс/инструмент так, чтобы ошибка была невозможна**.

## Andon — визуальный сигнал о проблеме

«Andon» (行灯) — японский бумажный фонарь. В TPS — лампа, шнур, табло, **которое любой оператор может активировать** при проблеме. Линия останавливается, проблема решается **здесь и сейчас**, не накапливается дальше.

**Культурный шок:** в Toyota оператор может остановить целую линию (потери — миллионы йен). И его за это **похвалят**, а не уволят. Потому что одна остановленная линия дешевле, чем 100 машин с дефектом, доехавших до клиента.

### Применение

- **Производство:** шнур над конвейером + табло над цехом со статусом всех линий.
- **Магазин:** красная кнопка «зови менеджера», которая мигает на смежном пульте.
- **Дашборд:** KPI зашкалил → красный + автоматический ping в Slack.
- **Закупки:** SKU попала в out-of-stock в 3+ магазинах → andon-алерт категорийщику.

## Heijunka — выравнивание производства

Инструмент против **Mura** (см. [[02-8-wastes-Muda-Mura-Muri|02]]). Идея: вместо «понедельник — 100 шт A, вторник — 100 шт B, среда — 100 шт C» делать **AAABBBCCC** микропартиями весь день.

### Зачем

- Снижает запасы (не нужно держать недельный буфер каждого типа).
- Снижает Lead Time (клиент чаще получает любой из видов).
- Снижает усталость и брак (равномерная нагрузка людей и оборудования).

### Heijunka box

Деревянный/пластиковый ящик с ячейками: горизонталь = время дня (по takt), вертикаль = тип продукта. В ячейку кладётся kanban-карточка → визуальный план дня для всех.

### Применение

В ритейле — **rolling promo plan**: вместо 3 акций по 4 недели в год — 12 акций по 1 неделе равномерно. Меньше пиковых нагрузок на склад, меньше overstock после акции.

В офисе — равномерное распределение задач: вместо «все отчёты в последнюю неделю месяца» — еженедельный rolling close.

## JIT — Just-in-Time

Производить **то, что нужно, в нужном количестве, в нужное время**. Один из двух столпов TPS (см. [[01-Toyota-Production-System|01]]).

JIT — это **результат**, а не инструмент. Чтобы JIT работал, нужно:
- Стабильный takt time
- Pull-сигналы (Kanban)
- Низкое время переналадки (SMED)
- Надёжное оборудование (TPM)
- Качество встроено в процесс (Jidoka)
- Quick problem solving (Andon, A3)

**Ловушка:** многие компании пытаются «внедрить JIT» — переходят на минимальные запасы, не построив фундамент. Результат: первый сбой поставки = простой производства.

## SMED — Single-Minute Exchange of Die

Цель: **переналадка оборудования за <10 минут** (single-digit minutes).

История: Сигео Синго (Shigeo Shingo) в 1969-м на Toyota сократил переналадку штамповочного пресса с 4 часов до 3 минут.

### Алгоритм SMED

1. **Разделить** все шаги переналадки на:
   - **Internal setup (IED)** — может быть сделан только при остановленной машине
   - **External setup (OED)** — может быть сделан, пока машина ещё работает
2. **Перевести** IED в OED — максимум подготовительных работ сделать заранее.
3. **Упростить** оставшийся IED: быстросъёмные крепления вместо болтов, цветовая маркировка, шаблоны.

### Зачем

Длительная переналадка = выгодно работать большими партиями = большие запасы, медленный поток. Короткая переналадка = можно делать мелкими партиями = низкие запасы, быстрый поток.

### В офисе

«Переналадка» = переключение между задачами. Если у сотрудника нужно 30 мин, чтобы «втянуться» в новый отчёт — это IED. Зачем держать одинаковый шаблон, заранее открытый? Это OED.

## TPM — Total Productive Maintenance

Цель: **поломки оборудования = ноль**. Подход: каждый оператор отвечает за состояние своего оборудования (autonomous maintenance), плюс плановое обслуживание + предиктивное обслуживание.

### 8 столпов TPM

1. Autonomous maintenance — сам оператор
2. Planned maintenance — плановое
3. Quality maintenance
4. Focused improvement (kaizen)
5. Early equipment management
6. Education & training
7. Safety & environment
8. TPM in admin / office

### OEE — главная метрика

**Overall Equipment Effectiveness = Availability × Performance × Quality**

- Availability = время работы / плановое время (потери от поломок и переналадок)
- Performance = реальный темп / паспортный (потери от мелких остановок и снижения скорости)
- Quality = годных / всего (потери от брака)

OEE 85%+ — мировой класс. Большинство компаний начинают с 40–50% и не знают этого.

## A3 Thinking — структурирование решения проблемы

«A3» — формат бумаги (297×420 мм), на котором Toyota заставляла менеджеров **уместить весь анализ проблемы**.

### Структура A3

```
ЛЕВАЯ ПОЛОВИНА (анализ — сначала понять):
├─ 1. Background / Context — почему эта проблема важна
├─ 2. Current Condition — что мы имеем сейчас (с цифрами и графиками)
├─ 3. Goals / Target — куда хотим прийти (S.M.A.R.T.)
├─ 4. Root Cause Analysis — 5 Why, fishbone, что мы реально решаем

ПРАВАЯ ПОЛОВИНА (действие):
├─ 5. Countermeasures — что делаем
├─ 6. Implementation Plan — кто, что, когда
├─ 7. Follow-up / Verification — как проверяем эффект, когда возвращаемся
```

<!-- IMG: A3 template | https://www.lean.org/lexicon-terms/a3-report/ -->

### Зачем

- **Дисциплина мышления:** заставляет идти от факта → анализа → решения, а не наоборот («у меня есть решение, теперь придумаю проблему»).
- **Коммуникация:** один лист = один взгляд = меньше power-point-инфляции.
- **Менторство:** A3 — это часто диалог менеджера с подчинённым: «принеси A3, обсудим».

### В офисе/закупках

A3 — отлично работает для:
- Решения «почему пересортица на приёмке».
- Запуска новой категории.
- Cost-out проекта по поставщику.

## PDCA — цикл Деминга

**Plan → Do → Check → Act**. Базовая логика любого улучшения. Внутри одного A3 может быть несколько циклов PDCA.

| Шаг | Действие |
|-----|----------|
| **Plan** | Сформулировать гипотезу: «если сделаем X, получим Y» |
| **Do** | Эксперимент в малом масштабе (на 1 SKU, 1 магазине, 1 неделе) |
| **Check** | Сравнить факт с гипотезой |
| **Act** | Если работает — стандартизовать. Если нет — извлечь урок и новый цикл |

PDCA — это **способ обучения через эксперимент**. Не «один раз внедрили и забыли», а постоянная итерация.

## Standard Work — стандартная работа

Самый недооценённый инструмент. **Без стандарта нет kaizen.** Если каждый делает по-своему, то «улучшение» = смена одного хаоса на другой.

### Что включает Standard Work

1. **Takt time** — ритм клиента
2. **Sequence of work** — последовательность шагов
3. **Standard WIP** — сколько единиц должно быть в процессе

### Принцип

«Стандартная работа — это **текущая лучшая известная практика**, обязательная для исполнения, пока не заменена улучшенной.»

→ Стандарт не «обездвиживает» процесс, наоборот — даёт базу, относительно которой видно эффект kaizen.

## Дополнительные инструменты (короткий список)

| Инструмент | Назначение |
|------------|------------|
| **5 Why** | Углубление в коренную причину через 5 последовательных «почему» |
| **Ishikawa / Fishbone** | Категоризация причин: Man/Method/Machine/Material/Measure/Environment |
| **Pareto** | 80/20 — какие 20% причин дают 80% эффекта |
| **Spaghetti diagram** | Визуализация лишних перемещений |
| **Visual management** | Дашборды, цвет, формы, расположение — всё, что показывает статус без слов |
| **Hoshin Kanri** | Стратегическое каскадирование целей (X-matrix), см. [[07-For-the-manager\|07]] |
| **Catch-ball** | Двусторонний диалог при каскадировании Hoshin |
| **Yokoten** | Горизонтальное распространение успешного kaizen на другие участки |

## Как НЕ внедрять инструменты (типичные ошибки)

1. **Начать с инструментов, минуя философию.** «Внедрим 5S и Kanban» без понимания TPS-фундамента → cargo cult.
2. **Tool-of-the-month.** Этот квартал — 5S, следующий — VSM, потом — Six Sigma. Сотрудники путаются.
3. **Top-down без gemba.** Менеджер прочитал книгу, скачал шаблоны, спустил вниз. Не работает.
4. **Без metrics-loop.** Внедрили, не измерили, не закрепили — откатилось.
5. **Не учли Mura/Muri.** Запустили kaizen на overstock, но оставили продавцов в режиме 12-часовых смен — пожаром обернётся.

Подробнее про культурные ошибки внедрения — в [[07-For-the-manager#Как-НЕ-внедрять-Lean|07]].

## Что забрать руководителю

1. **Инструменты — следствие, культура — причина.** Без TPS-фундамента (см. [[01-Toyota-Production-System|01]]) инструменты не приживаются.
2. **Начинать с VSM** — он показывает реальные потери, а не предполагаемые.
3. **5S — стартовая практика на любом физическом пространстве** (склад, цех, шоурум). Дёшево, видимо, объединяет команду.
4. **Kanban + Heijunka — главные инструменты против Inventory и Mura.** В закупках / ритейле это основные враги.
5. **A3 + PDCA — главные инструменты решения проблем.** Стоит сделать нормой работы команды.
6. **Standard Work — обязательное условие любых улучшений.** Без него улучшения — дом на песке.
